# deploy

Инфраструктура NetStream-Core: приём телеметрии от агентов и хранение.

```
agent --OTLP--> otel-edge --> Kafka --> otel-gateway --> ClickHouse
```

| Сервис | Образ | Назначение |
|---|---|---|
| `otel-edge` | `otel/opentelemetry-collector-contrib:0.161.0` | Принимает OTLP от агентов (gRPC 4317, HTTP 4318), пишет в Kafka |
| `kafka` | `confluentinc/cp-kafka:7.9.10` | Буфер между приёмом и хранением (KRaft, один брокер, хранение 7 дней) |
| `gateway`, `victim`, `attacker`, `client` | собираются из `lab/` | Лаборатория для датасета (только с `compose.lab.yml`) |
| `otel-gateway` | `otel/opentelemetry-collector-contrib:0.161.0` | Читает из Kafka, пишет в ClickHouse |
| `clickhouse` | `clickhouse/clickhouse-server:25.8` | Хранилище потоков, DNS-событий и срабатываний блоклиста |
| `migrate` | `clickhouse/clickhouse-server:25.8` | Применяет миграции из `clickhouse/migrations` |
| `grafana` | `grafana/grafana:12.4.11` | Дашборды поверх ClickHouse (плагин `grafana-clickhouse-datasource` 4.21.3, ставится при первом запуске) |
| `kafka-ui` | `provectuslabs/kafka-ui:v0.7.2` | Отладка, только с `--profile debug` |
| `objectstore` | `chrislusf/seaweedfs` 4.48, закреплён по digest | S3-совместимое объектное хранилище для артефактов моделей (`backend`); S3 API на порту 8333 |

`objectstore` — SeaweedFS, а не MinIO: официальный образ `minio/minio` с 2025 года требует `docker login` даже для анонимного pull (включая старые теги), что делает его непригодным для CI и для `docker compose up` без предварительной настройки учётной записи. SeaweedFS даёт тот же S3 API (клиент — `minio-go`, он работает с любым S3-совместимым сервером, не только с MinIO) без этого ограничения. Доступ — статический ключ в `objectstore/s3-config.json` (`netstream`/`netstream-dev`, как и остальные dev-учётки в этом репозитории), бакет `netstream-models` создаётся автоматически при первой загрузке.

## Запуск

```bash
just up        # docker compose up -d
just ps
just sql       # clickhouse-client внутри контейнера
just demo      # запуск и демо-данные с «атаками» (см. ниже)
just lab-up    # лаборатория с реальными атаками (см. «Лаборатория»)
just down      # остановить, данные сохраняются
just reset     # остановить и удалить данные
```

Порты открыты только на `127.0.0.1` и переопределяются через `.env` (см. `.env.example`): `EDGE_GRPC_PORT`, `EDGE_HTTP_PORT`, `KAFKA_HOST_PORT`, `CLICKHOUSE_HTTP_PORT`, `CLICKHOUSE_NATIVE_PORT`, `GRAFANA_PORT`. Учётные данные ClickHouse по умолчанию (`netstream` / `netstream-dev`) предназначены только для локальной разработки.

Помимо суперпользователя `netstream` (нужен `migrate` для DDL и collector'ам для записи), миграция `013_read_only_role.sql` заводит роль `netstream_reader` (`SELECT` на `netstream.*` и на `system.tables`/`system.columns` для автодополнения) и пользователя `netstream_ro` / `netstream-ro-dev`. Grafana ходит в ClickHouse именно под ним (см. `grafana/provisioning/datasources/clickhouse.yml`) — панель не может ничего испортить, даже если кто-то допишет `INSERT`/`DROP` в `rawSql`. Пароль зашит в саму миграцию (`migrate.sh` не подставляет переменные окружения в `.sql`-файлы), поэтому `CLICKHOUSE_RO_USER`/`CLICKHOUSE_RO_PASSWORD` в `compose.yml` не читаются из `.env` — меняются оба места разом, если понадобится сменить пароль. Тому же аккаунту стоит пользоваться и `ml` (`netstream-ml data export --user netstream_ro --password netstream-ro-dev ...`), поскольку он только читает.

Агент направляется на `http://127.0.0.1:4317` (по умолчанию так и есть, см. `OTEL_EXPORTER_OTLP_ENDPOINT`).

## Миграции

Файлы `clickhouse/migrations/NNN_*.sql` применяются раннером `migrate` по порядку и один раз каждый; применённые версии записываются в `schema_migrations`. Раннер запускается при каждом `up`, поэтому схема развивается на непустой базе. Уже применённый файл менять нельзя: изменение оформляется новой миграцией.

`migrate.sh` гоняет каждый файл через `clickhouse-client --multiquery`, который не оборачивает несколько операторов внутри файла в одну транзакцию (ClickHouse транзакций DDL не поддерживает) — если второй оператор файла падает, первый уже применён к схеме, а строка в `schema_migrations` для всего файла не появляется (`INSERT` идёт только после успеха всех операторов). При повторном запуске файл накатывается заново **с первого оператора**, поэтому каждая миграция обязана быть безопасной при полном повторе: `CREATE TABLE`/`ADD COLUMN` — только с `IF NOT EXISTS`, пересоздание view — через `CREATE OR REPLACE VIEW` или предварительный `DROP VIEW IF EXISTS`. `just migrations-test` (`tests/clickhouse/migrations.sh`) проверяет это на реальном ClickHouse: что все миграции из `clickhouse/migrations/` реально применяются по порядку с чистой базы, что повторный прогон — no-op, и что искусственно подставленная падающая на втором операторе миграция оставляет первый оператор применённым, но саму миграцию — неотмеченной в `schema_migrations`, а после исправления повторный запуск накатывает её чисто, не трогая уже применённые.

| Таблица | Содержимое | Хранение |
|---|---|---|
| `otel_logs` | Сырые записи от collector, промежуточный слой | 3 дня |
| `flows` | Дельты по потокам за интервал съёма | 14 дней |
| `dns_queries` | DNS-запросы с признаками | 14 дней |
| `blocklist_hits` | Срабатывания блоклиста | 90 дней |
| `flows_1m` | Суммы по минутам (host, направление, транспорт) | 90 дней |
| `otel_metrics_gauge`, `otel_metrics_sum`, `otel_metrics_histogram` | Сырые метрики агента от collector, промежуточный слой | 3 дня |
| `agent_metrics` | Метрики накладных расходов агента (`netstream_*`), объединены gauge и sum | 30 дней |
| `detections` | Срабатывания онлайн-детектора из `netstream.detections.v1` (подробнее — раздел «Топик `netstream.detections.v1`» ниже) | 90 дней |

Типизированные таблицы заполняются materialized views из `otel_logs` по полю `EventName`; `agent_metrics` — из `otel_metrics_gauge`/`otel_metrics_sum` по `MetricName`. Схема `otel_metrics_*` и `otel_logs` продиктована экспортёром `clickhouseexporter` (`create_schema: false` — таблицы должны существовать и совпадать по колонкам заранее, экспортёр их не создаёт). `detections` — единственная таблица, заполняемая не через `otel-gateway`: `netstream.detections.v1` несёт обычный JSON, а не OTLP, поэтому её читает напрямую движок ClickHouse `Kafka` (`detections_queue` → materialized view `detections_mv`) — тот же паттерн, которым читаются остальные топики, но без промежуточного collector'а, раз тут нет OTLP, под который заточен `clickhouseexporter`.

Дашборд Grafana «NetStream / Sensor health» строится на `agent_metrics`: память, загрузка таблицы потоков, время выполнения BPF-программ, потери в DNS ring buffer и переполнения бюджета новых потоков — отдельно от дашбордов трафика, поэтому ловит поломку самой телеметрии агента (сенсор жив и шлёт потоки, но метрики перестали доходить, или наоборот).

## Контракт событий

Агент отправляет OTLP-логи. Тип события задаётся полем `event_name` записи, числа передаются целыми (`intValue`), а не строками. Имена атрибутов следуют семантическим соглашениям OpenTelemetry там, где они есть.

**Resource-атрибуты** (общие для всех записей агента)

| Атрибут | Пример |
|---|---|
| `service.name` | `netstream-monitor-agent` |
| `host.id` | идентификатор сенсора |
| `service.instance.id` | случайный `boot_id`, новый при каждом перезапуске агента (колонка `boot_id`) |
| `network.interface.name` | `eth0` |

**Идентичность события** (есть у `netstream.flow`, `netstream.dns.query`, `netstream.blocklist.hit`)

| Атрибут | Тип | Колонка |
|---|---|---|
| `netstream.event.sequence` | int, монотонный счётчик от 0 в пределах одного `boot_id` | `event_sequence` |
| `netstream.event.id` | `"{boot_id}-{sequence}"`, уникален за всю историю сенсора | `event_id` |

`event_id`/`event_sequence` позволяют отличить повтор события (Kafka retry, повторная доставка) от нового события и понять, что перед этой записью агент перезапускался (`boot_id` сменился, `event_sequence` начался заново с 0). `ts` в типизированных таблицах — это `event_time`: когда агент сформировал запись (для потока — конец интервала съёма, а не момент конкретного пакета). `ingest_time` — отдельная колонка, момент вставки строки в `otel_logs` (`DEFAULT now()`, не приходит от агента) — разница `ingest_time - ts` и есть задержка доставки телеметрии, отдельная от задержки детектирования.

**Дедупликация по `event_id` не выполняется ни при записи, ни в материализованных представлениях** — `flows`/`dns_queries`/`blocklist_hits` используют обычный `MergeTree`, не `ReplacingMergeTree`, и строка с уже виденным `event_id` просто вставляется второй раз. Источник возможного дубля — ровно один: `retry_on_failure` в `collector/edge.yaml`/`edge-tls.yaml` переотправляет весь батч OTLP-записей, если `otel-edge` не получил подтверждение от Kafka вовремя, в том числе если запись на самом деле уже дошла и подтверждение просто не успело вернуться — редкое окно, не постоянный источник дублей. Решение осознанное, а не упущение: `ReplacingMergeTree` потребовал бы `FINAL` (или `argMax`-агрегацию) во всех запросах поверх этих таблиц — дашбордах Grafana, `flows_1m`, e2e-тестах — то есть переписать аналитический слой целиком ради события, которое почти никогда не происходит, вместо того чтобы просто дать потребителю, которому точность важна, способ отфильтровать дубль на чтении:

```sql
SELECT * FROM (
    SELECT *, row_number() OVER (PARTITION BY event_id ORDER BY ingest_time) AS rn
    FROM flows WHERE event_id != ''
) WHERE rn = 1
```

(`event_id = ''` — строки, записанные до миграции `014_event_identity.sql`; для них идентичности нет и дедуплицировать нечем, в выборку выше их нужно включать отдельно as-is.) `netstream.detections.v1`/таблица `detections` в этом не нуждается — Kafka-движок ClickHouse сам читает её `JSONEachRow`-сообщения один раз per offset, а повторная публикация детекции онлайн-детектором (после незакоммиченного офсета, см. `ml/README.md`) создаёт новую строку с тем же `(host_id, src_ip, window_start, window_seconds)`, не с тем же `event_id` — это тот же компромисс, с тем же обоснованием: редкое событие, различимое по стабильному ключу при чтении, а не склеенное при записи.

**`netstream.flow`**: дельта по потоку за интервал

| Атрибут | Тип | Колонка |
|---|---|---|
| `network.io.direction` | `receive` или `transmit` | `direction` |
| `network.transport` | `tcp`, `udp`, `icmp`, другое | `transport` |
| `source.address`, `destination.address` | IPv4 | `src_ip`, `dst_ip` |
| `source.port`, `destination.port` | int | `src_port`, `dst_port` |
| `netstream.flow.interval_ms` | int | `interval_ms` |
| `netstream.flow.packets` | int | `packets` |
| `netstream.flow.bytes.ip`, `netstream.flow.bytes.payload` | int | `ip_bytes`, `payload_bytes` |
| `netstream.flow.tcp.syn`, `.synack`, `.fin`, `.rst` | int | `tcp_syn`, `tcp_synack`, `tcp_fin`, `tcp_rst` |
| `netstream.flow.aggregated` | 0, 1 или 2 | `aggregated` |
| `netstream.flow.size.le64`, `.le128`, `.le256`, `.le512`, `.le1024`, `.gt1024` | int | `size_le64`, `size_le128`, `size_le256`, `size_le512`, `size_le1024`, `size_gt1024` |
| `netstream.flow.iat.count`, `.sum_us`, `.sumsq_us` | int | `iat_count`, `iat_sum_us`, `iat_sumsq_us` |

Признаки формы потока: `size.*` разбивают пакеты интервала на непересекающиеся корзины по полной длине IP-пакета (до 64, 65-128, 129-256, 257-512, 513-1024 и свыше 1024 байт), `iat.*` накапливают межпакетные интервалы внутри потока в микросекундах (число интервалов, сумма и сумма квадратов, интервал ограничен 10 с). Среднее и разброс считаются как `sum / count` и `sqrt(sumsq / count - (sum / count)^2)`. Интервалы измеряются на ядре CPU, обрабатывающем поток, первый пакет потока интервала не даёт.

Порт `0` в записи потока означает, что агент объединил порт: эфемерный порт клиента при обычном трафике. Когда исчерпан бюджет новых потоков (флуд с меняющимися портами), пакеты попадают в агрегированные потоки: при `aggregated = 1` объединён только порт источника (порт назначения сохранён, так виден и флуд по одному порту, и сканирование), при `aggregated = 2` объединены оба порта. Суммы пакетов и байт при этом сохраняются полностью.

**`netstream.dns.query`**: один DNS-запрос

| Атрибут | Тип | Колонка |
|---|---|---|
| `network.io.direction` | `receive` или `transmit` | `direction` |
| `network.transport` | `tcp` или `udp` | `transport` |
| `source.address`, `destination.address` | IPv4 | `src_ip`, `dst_ip` |
| `dns.question.name` | string, нижний регистр | `qname` |
| `netstream.dns.question.type` | `A`, `TXT`, `NULL`, `AAAA`, … | `qtype` |
| `netstream.dns.qname.length`, `.labels`, `.longest_label` | int | `qname_length`, `label_count`, `longest_label` |
| `netstream.dns.qname.entropy`, `.digit_ratio` | double | `entropy`, `digit_ratio` |
| `netstream.dns.unique_subdomains` | int | `unique_subdomains` |

**`netstream.blocklist.hit`**: срабатывание блоклиста

| Атрибут | Тип | Колонка |
|---|---|---|
| `source.address` | IPv4 | `src_ip` |
| `netstream.hit.domain` | string | `domain` |
| `netstream.hit.action` | `observed`, `dropped`, `quarantined` | `action` |

Метки времени записи (`timeUnixNano`) попадают в `ts`.

## Дашборды

Grafana доступна на `http://127.0.0.1:3000` (пользователь `admin`, пароль по умолчанию `netstream-dev`, только для разработки). Дашборды загружаются из `grafana/dashboards` и в интерфейсе не редактируются: изменения вносятся в JSON. Для демонстраций без входа можно задать `GRAFANA_ANONYMOUS=true`: тогда открывается режим только для чтения (только на локальной машине).

| Дашборд | Что показывает |
|---|---|
| `NetStream / Traffic` | Пакеты и объём по направлениям, TCP-рукопожатия и отношение SYN к SYN-ACK (признак SYN-flood), число различных портов назначения на источник (признак сканирования), самые активные пары адресов, доля транспортов, время последней записи от каждого сенсора |
| `NetStream / DNS and blocklist` | Запросы по типам, длина и энтропия имён, число уникальных поддоменов (признак DNS-туннелирования), подозрительные запросы, домены с наибольшим числом уникальных имён, срабатывания блоклиста по действиям |
| `NetStream / Sensor health` | Накладные расходы и работоспособность самого агента: память, загрузка таблицы потоков, время выполнения BPF-программ, потери в кольцевых буферах (подробнее — раздел «Миграции» выше) |
| `NetStream / Detections` | Срабатывания онлайн-детектора (`ml/ml-online-detector`, M16) из `netstream.detections.v1`: число атак и окон за период, p50/p95 задержки обнаружения, таймлайн по сенсору, таблица последних детекций |

Переменная **Sensor** фильтрует данные по `host_id`. Сведённые к минутам панели читают `flows_1m`, детальные (таблицы, порты) читают `flows`.

## Лаборатория для датасета

Стенд из четырёх контейнеров поверх основного стека. Агент работает на шлюзе и видит трафик так, как его видел бы сенсор в реальной сети.

```
attacker 10.10.0.10 ┐                               ┌ victim 10.20.0.10 (nginx, dnsmasq)
                    ├── lan ── gateway (агент) ── dmz ┘
client   10.10.0.20 ┘         10.10.0.2 / 10.20.0.2
```

Агент подключается к LAN-интерфейсу шлюза: входящий трафик клиентов и атакующего он видит через XDP, ответы жертвы через TC. Обычный клиент (`client`) постоянно создаёт фоновый трафик (HTTP-запросы и DNS-запросы обычных имён), поэтому атаки происходят на фоне нормальной активности.

```bash
just lab-agent ../agent      # копирует release-бинарник (eBPF встроен в него) и git-ревизию агента
just lab-up                  # стек и лаборатория
just lab-run syn_flood duration=30 rate=1000
just lab-run port_scan ports=1-1024 rate=100
just lab-run dns_tunnel duration=30 rate=20 qtype=mixed
just lab-run c2_beacon duration=30 rate=2
just lab-down
```

Помимо `attacker`, `victim` и `client` в лаборатории есть контейнер `tunnel` (10.20.0.20): сервер `iodined` для настоящего DNS-туннеля, а не только эмуляции. У `victim` также есть SSH и `iperf3` для сценариев доброкачественной нагрузки.

Docker Desktop нужен на Linux-ядре с поддержкой eBPF (проверено на `6.10.14-linuxkit`); шлюз запускается в привилегированном контейнере, права `sudo` на хосте не требуются.

**Атаки**

| Сценарий | Инструмент | Метка | Параметры (по умолчанию) |
|---|---|---|---|
| `syn_flood` | `hping3 -S` | `syn_flood` | `rate` пакетов/с (1000), `duration` (30), `port` (80), `keep=1` фиксирует порт источника, `flood=1` без ограничения скорости |
| `udp_flood` | `hping3 --udp` | `udp_flood` | `rate` (1000), `duration` (30), `size` байт (512), `flood=1` |
| `icmp_flood` | `hping3 --icmp` | `icmp_flood` | `rate` (1000), `duration` (30), `size` (512), `flood=1` |
| `port_scan` | `nmap -sS` | `port_scan` | `ports` (1-1024), `rate` пакетов/с (100), `timing` (4) |
| `slow_scan` | `nmap -sS -T2` | `port_scan` | `ports` (1-60), `rate` (2): низкая скорость, малый разброс портов |
| `slowloris` | `slowhttptest` | `slowloris` | `conns` соединений (50), `rate` заголовков/с (50), `duration` (30) |
| `dns_tunnel` | `dns_tunnel.py`, эмуляция туннеля | `dns_tunnel` | `rate` запросов/с (20), `duration` (30), `qtype` `TXT`, `NULL` или `mixed` |
| `iodine_tunnel` | `iodine` через контейнер `tunnel`, настоящий DNS-туннель | `dns_tunnel` | `duration` (30): скачивает файл через `dns0` |
| `c2_beacon` | `beacon.py` | `c2_beacon` | `rate` (2), `duration` (30): запросы к домену из блоклиста |

**Доброкачественный трафик**, включая профили, специально похожие на атаки (нужны, чтобы оценка ML не была завышена из-за слишком чистого фона)

| Сценарий | Инструмент | Источник | Похож на |
|---|---|---|---|
| `benign` | `benign.py` (фоновый клиент, работает всегда) | `client` | — |
| `bulk_download` | `iperf3` TCP | `client` | флуд по объёму трафика |
| `udp_stream` | `iperf3 --udp` | `client` | UDP-флуд по объёму |
| `video_stream` | `curl --limit-rate` | `client` | устойчивый поток |
| `web_burst` | `ab` (ApacheBench) | `client` | SYN-флуд по числу соединений в секунду |
| `ssh_session` | `ssh` (`sshpass`), интерактивная сессия | `client` | долгий тихий поток |
| `backup` | `ssh` с потоком через `dd` | `client` | объём как у флуда, порт 22 |
| `cdn_dns` | `dns_profile.py --kind cdn` | `client` | случайные поддомены как у CDN |
| `dkim_dns` | `dns_profile.py --kind dkim` | `client` | TXT-запросы как у DNS-туннеля |
| `reputation_dns` | `dns_profile.py --kind reputation` | `client` | длинные, высокоэнтропийные имена как у туннеля |
| `admin_scan` | `nmap -sS -T3` | `client` | сканирование портов от своего клиента |

`admin_scan` неотличим от `port_scan` по признакам потока — их разделяет только адрес источника. Модель, обученную на этих данных, стоит проверять на нём отдельно от общего FPR.

Каждый запуск записывается в таблицу `labels`: сценарий, метка, инструмент, параметры, адреса атакующего и жертвы, начало и конец окна. Времена берутся с часов шлюза, на которых агент ставит метки записям.

**Размеченные данные.** Представления `labeled_flows` и `labeled_dns` добавляют к записям столбцы `label` и `run_id`: запись относится к атаке, если её источник или получатель это адрес атакующего и время попадает в окно запуска. Всё остальное получает метку `benign`. Для потоков учитывается, что запись создаётся в конце интервала съёма (`ts - interval_ms` до `ts`), для DNS-запросов добавляется допуск в секунду.

```sql
SELECT label, count() AS records, sum(packets) AS packets FROM labeled_flows GROUP BY label;
```

**Ограничения.**
- Флуд с меняющимися портами (`hping3` берёт порты из всего диапазона) не должен ни терять пакеты, ни порождать поток на каждый пакет. Агент ограничивает число новых потоков на каждое ядро (`FLOW_NEW_PER_SECOND`, по умолчанию 320 в секунду), а остальные пакеты считает в агрегированном потоке пары адресов без портов. Тест лаборатории сравнивает счёт агента со счётчиком интерфейса шлюза на неограниченном флуде. Внутри агрегированных потоков теряется различие портов: скорости выше бюджета ядер (`FLOW_NEW_PER_SECOND`, для сохранения портов назначения он умножается на 10) занижают число различных портов.
- Источник адресов в атаках не подделывается: метка определяется по адресу атакующего.
- `dns_tunnel` (эмуляция) и `iodine_tunnel` (настоящий инструмент) дают разные признаки: у `iodine` энтропия имён ниже, а тип записи фиксированный (`NULL`), у эмуляции выше и `TXT`/`NULL` можно выбирать. Для проверки на смещение (M11) стоит использовать оба.
- Все узлы работают на одной машине и одном ядре, поэтому задержки и потери не соответствуют реальной сети.

## Кампании

Кампания — это список запусков сценариев по YAML-файлу (`lab/campaigns/v1.yaml`): интенсивности, повторы, доброкачественные профили. Оркестратор поднимает лабораторию, ждёт готовности, прогоняет каждый сценарий с паузой между ними (фоновый трафик клиента продолжается всё время) и пишет манифест со сверкой числа запусков, git-ревизией `deploy` и `agent` (из `build_info.json`, который кладёт `just lab-agent`), контрольной суммой файла кампании и списком размеченных запусков из таблицы `labels`.

```bash
just lab-agent ../agent
just lab-campaign lab/campaigns/v1.yaml
```

Манифест уходит в `lab/campaigns/manifests/<кампания>-<время>.json` (не в git). По умолчанию оркестратор поднимает и останавливает лабораторию сам; `--skip-up` и `--skip-down` дают собрать несколько кампаний подряд без пересоздания стека. `--gap-seconds` переопределяет паузу между запусками из файла.

## Тесты

```bash
just e2e
```

Тест поднимает отдельный проект `netstream-e2e` на свободных портах, отправляет три записи через edge-collector и проверяет: содержимое типизированных таблиц и агрегата, идемпотентность миграций, то, что при остановленном gateway данные накапливаются в Kafka и доходят после его запуска, что Grafana поднимает источник данных и оба дашборда, и что всплеск из десятков тысяч записей сохраняется без потерь. `KEEP=1 just e2e` оставляет стек запущенным для отладки. Общие хелперы (`free_port`, `check`/`eventually`, конструкторы OTLP-записей) вынесены в `tests/e2e/lib.sh`, им пользуется и `run.sh`, и `detection.sh` ниже.

```bash
just e2e-detect
```

Сквозной тест онлайн-детектора (P1 из внешнего ревью): поднимает Kafka/edge/ClickHouse (без gateway/Grafana — детектору они не нужны), публикует настоящую (хоть и тривиальную) ONNX-модель и запускает `detect run` как обычный процесс на хосте (`uv run --project ../ml`, тот же принцип, что и у `tools/seed.py`), затем шлёт синтетические окна через edge и проверяет: детекция реально доходит до таблицы `detections` в ClickHouse; после остановки детектора новые события не обрабатываются, а после перезапуска подхватываются из закоммиченного офсета без потери и без повторной обработки уже закрытого окна; при кратковременной недоступности Kafka процесс не падает и продолжает детектировать после восстановления брокера. `idle-flush-seconds` здесь заметно больше паузы между тестовыми записями (иначе принудительное закрытие окна по таймеру срабатывает раньше, чем запись, которая должна закрыть его естественным образом, и получается двойная детекция на одну пару записей).

```bash
just migrations-test
```

Проверка на реальном ClickHouse, что миграции применяются по порядку и восстанавливаются после падения на середине файла — подробности в разделе «Миграции» выше.

`just lab-e2e` запускает лабораторию, выполняет все сценарии и проверяет размеченные данные.

CI (`.github/workflows/ci.yaml`) на каждый PR прогоняет `yamllint` по всем YAML-файлам (`.yamllint.yaml`), проверяет `docker compose config` для основного стека и лабораторной надстройки и валидирует конфиги `otel-edge`/`otel-edge-tls`/`otel-gateway`. Это только синтаксис и совместимость версий compose — `just e2e`/`just e2e-detect`/`just lab-e2e`/`just migrations-test` с реальными контейнерами CI не запускает (нужен eBPF и много ресурсов для лаборатории; остальные просто пока не вынесены туда), их гоняют локально.

## TLS

Приём OTLP от агентов (`otel-edge`) можно включить с TLS — `EDGE_CONFIG_FILE=edge-tls.yaml` в `.env` вместо конфига по умолчанию (`edge.yaml`), сертификат и ключ в `./certs/tls.crt`/`./certs/tls.key` (директория всегда монтируется в контейнер, путь `/certs`; без TLS-конфига просто не используется). Только серверный TLS — `otel-edge` подтверждает себя сертификатом агенту, обратной аутентификации нет; та же модель, что и у `backend` (см. его README, раздел «TLS») и по той же причине — закрывает MITM на пути между агентом и edge, не отвечает на вопрос «какой конкретно агент это послал».

Самоподписанный сертификат для лаборатории — та же команда и та же оговорка про `basicConstraints=CA:FALSE`, что у `backend`:

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
    -keyout certs/tls.key -out certs/tls.crt -subj "/CN=localhost" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "keyUsage=digitalSignature,keyEncipherment" \
    -addext "extendedKeyUsage=serverAuth" \
    -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

Агент указывает этот же сертификат в `OTEL_EXPORTER_OTLP_CERTIFICATE` (см. `agent/README.md`, раздел «TLS» под «Телеметрия») и `https://` в `OTEL_EXPORTER_OTLP_ENDPOINT`. Проверено вживую: настоящий агентский экспортёр прошёл TLS handshake с этим конфигом и реально доставил события до Kafka (offset топика `netstream.events.v1` вырос) — не просто «конфиг выглядит правильным».

`edge-tls.yaml` — отдельный файл, не параметризация `edge.yaml` через переменные окружения: OTel Collector не поддерживает условное отсутствие целого блока (`tls:`) на основе env var, только подстановку значений внутри уже существующих ключей. Оба файла держать синхронными (processors/exporters идентичны, разница только в `receivers.otlp.*.tls`) — на это нет отдельной проверки, кроме визуального ревью при правках одного из них.

## Ограничения

- Размер сообщения Kafka ограничен: edge собирает батчи по 1024 записи, сжимает их (zstd), лимит брокера и продюсера 4 МиБ. Слишком крупный батч отбрасывается без повторов, поэтому на это есть регрессионная проверка в e2e.
- Один брокер Kafka без репликации, без аутентификации; TLS опционален только на приёме OTLP (выше), сам брокер и `otel-gateway`→`ClickHouse` — без TLS. Конфигурация для разработки и стенда.
- Очередь отправки в edge-collector хранится в памяти: при его перезапуске непереданные данные теряются.

`netstream.events.v1` создаётся с тремя партициями (`kafka-init`), и Kafka не даёт порядок между разными партициями вообще — только в пределах одной. `ml-online-detector`'s `WindowAccumulator` это предполагает: закрывает окно, когда приходит более поздняя запись того же источника, а значит записи одного сенсора обязаны приходить в консюмер в том порядке, в котором агент их отправил. `exporters.kafka.partition_logs_by_resource_attributes: true` (`collector/edge.yaml`, `edge-tls.yaml`) обеспечивает это — партиция считается хэшем от ресурсных атрибутов батча (`host.id`, `service.instance.id` и т. д.), поэтому все записи одного сенсора за время жизни одного процесса агента стабильно попадают в одну партицию. `service.instance.id` — это `boot_id`, новый при каждом перезапуске агента, так что перезапуск может сменить партицию — это естественная точка разрыва порядка (новый `boot_id` и так начинает `event_sequence` заново), а не новая проблема. Проверено вживую: два отдельных батча OTLP-логов с одним и тем же `host.id` реально легли в одну и ту же партицию `netstream.events.v1`, а батч с другим `host.id` — в другую.

## Топик `netstream.detections.v1`

Третий топик, создаваемый `kafka-init` рядом с `netstream.events.v1` и `netstream.metrics.v1`. Пишет в него онлайн-детектор (`ml/ml-online-detector`, `netstream_ml.detector`, см. `ml/docs/online-detector.md`): отдельный процесс со своей consumer group, который читает тот же `netstream.events.v1`, что и `otel-gateway` для заполнения ClickHouse, независимо от него, и публикует результат оценки каждого закрывшегося окна признаков. Читает топик ClickHouse напрямую (таблица `detections`, движок `Kafka`, миграция `015_detections.sql` — см. «Миграции» выше); дашборд `NetStream / Detections` строится на этой таблице.

Каждое сообщение — JSON-объект (не OTLP, в отличие от `netstream.events.v1`/`netstream.metrics.v1`):

```json
{
    "host_id": "sensor-1",
    "src_ip": "10.0.0.5",
    "window_start": 1700000000,
    "window_seconds": 5,
    "score": 11.5,
    "is_attack": true,
    "latency_ms": 842.3
}
```

| Поле | Тип | Значение |
|---|---|---|
| `host_id` | string | сенсор, чей `WindowAccumulator` закрыл окно (`host.id` из resource-атрибутов `netstream.events.v1`) |
| `src_ip` | string | источник, к которому относится окно |
| `window_start` | int | unix-время (секунды) начала окна |
| `window_seconds` | int | длина окна |
| `score` | float | `decision_score` модели; не нормализовано и не сравнимо между разными моделями (детали — в README `ml-online-detector`) |
| `is_attack` | bool | решение модели |
| `latency_ms` | float | время между теоретическим концом окна (`window_start + window_seconds`) и моментом оценки; может быть отрицательным при принудительном `flush()` до конца окна — это ожидаемо, см. README `ml-online-detector` |

## Топик `netstream.alerts.v1`

Четвёртый топик, создаваемый `kafka-init`. Пишет в него `backend` (`internal/detections`, см. его README, раздел «Инциденты») — своя consumer group на `netstream.detections.v1`, своя логика: не каждая детекция, а только та, что открывает новый инцидент (повторные детекции по той же паре `(host_id, src_ip)` в течение 5 минут продлевают уже открытый инцидент и не производят новый алерт). Включается через `KAFKA_BOOTSTRAP_SERVERS` у backend — без неё топик создаётся, но никто в него не пишет.

```json
{
    "incident_id": 1,
    "host_id": "sensor-1",
    "src_ip": "10.0.0.5",
    "severity": "low",
    "opened_at": "2026-10-24T12:21:07.6252+03:00"
}
```

Пока без собственного потребителя в этом стеке — ни Grafana, ни ClickHouse на него не подписаны: оператор смотрит открытые инциденты через `GET /api/v1/incidents` backend'а, а этот топик существует для будущего потребителя (нотификации, вебхук), которому не нужно вычитывать весь `netstream.detections.v1` и повторять дедупликацию по инцидентам самостоятельно.
